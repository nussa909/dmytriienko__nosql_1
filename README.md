**Частина 1 — Завантаження даних та проєктування схеми**

*1. Чому аудіо-характеристики винесені в окремий об’єкт audio_features, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?*
 Думаю, таке розділення розділяє базові характеристики треку(назва, альбом, жанр тощо) від суто технічних характеристик. Це робить документ більш чибабільнішим. Це також може бути зручно, для відображення треку - технічні характеристики можна просто вимкнути із проекції одним рядком: { audio_features: 0 }.
 Таке розділення може бути не зручним, якщо треба складати запити з використанням технічних характеристик: звернення до параметра стає довшим(наприклад "$audio_features.energy").

<br>

*2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?*
Зберігання данних у вигляді массиву - це спосіб зберігати зв'язвк "багато-до-одного" або "багато-до-багатьох" без дублювання данних.
Які запити стають простішими:
- [x] db.tracks.find({ artists: "Queen" }) - база зможе пройтись по масиву і знайти пісню вказаного виконавця. У випадку з рядком довелося б розбивати рядок вручну або використовувати регулярні вирази.
- [x] документ з масивом можна розкласти на складові за допомогою \$unwind, а потім групувати, фільтрувати данні по кожному артисту. З рядком \$unwind також не працює.

<br>

*3. Що таке \$out і чим він відрізняється від \$merge? Коли використовувати кожен?*
Обидва оператори використовуються для збереження данних у коллекцію в базі данних на останьому етапі пайплайну. Відрізняються вони тим, що \$out повністю перезаписує коллекцію, тобто якщо коллекцію з такою назвою вже була - вона буде видалена. 
Оператор \$merge не видаляє стару колекцію, а намагається об'єднати/оновити нові результати з вже існуючими(мержить).

**Частина 2 — Запити до даних**
*1. Для чого використовується інструкція \$unwind?*
\$unwind використовується для розгортання масивів в документі. Замість одного документа з масивом створюється окрема копія документа для кожного елементу масива.
\$unwind можна використовувати як підготовчий етап перед групуванням, фільтрацією данні по кожному артисту. З рядком $unwind також не працює. 

<br>

*2. Чим \$stdDevPop відрізняється від \$stdDevSamp?*
Обидва оператора рахують стандартне відхилення (показує, наскільки значення відхиляється від середнього). Але \$stdDevPop використовується, коли мають в наявності всі можливі данні (популяція). Натомість \$stdDevSamp використовується, коли є лише частина данних(вибірка) від великої кількості данних і треба зробити глобальний прогноз про всіх.

**Частина 3 — Аналітика через Aggregation Pipeline**
*1. У запиті 1 ми фільтруємо виконавців, у яких менше 5 треків. Як зміниться результат, якщо знизити поріг до 1? А що станеться, якщо вибирати виконавців із більш ніж 50 треками? Поясніть результат.*
Якщо з знизити поріг до 1, то середня популярність суттєво збільшиться. В цьому випадку в вибірку попадуть виконавці із 1,але дуже популярним треком. Середня популярність у такого виконавця буде високою, але це значення не завжди буде відображати реальність.  
Якщо збільшити поріг до 50, то середня популярність зменшиться. В вибірку попадуть виконавці із більш ніж 50 треками, тобто це дуже плідні(можливо навіть легендарні) виконавці, мега-зірки. Їх середня популярність буде суттево нижчою, тому що вираховується як середнє арифметичне з 50 треків серед яких є як хіти, так і просто прохідні пісні.

<br>

*2. У запиті 3 ми фільтруємо жанри з менше ніж 100 треками. Чи зміниться результат, якщо знизити поріг до 50? Поясніть результат.*
Судячи із результатів запиту майже всі жанри в базі налічують ~1000 треків і тому коли ми вказуємо поріг в 100 або 50 треків - результат ніяк не змінюється. Пояснити це можна тим, що взятий з Kaggle датасет, скоріш за все був відбалансований за кількістю треків по жанрах.

*Завдання 3*
```
db.tracks.find({
  track_genre: "pop",
  popularity: { $gte: 70 }
});
```

*1. Чи є цей запит покривним (covered query)? Надайте розгорнуту та обґрунтовану відповідь у файлі README.*
Ні, цей запит не є покривним. Для того, щоб він став покривним мають бути виконані умови(згідно із конспектом):
- Усі поля в умовах фільтрації мають бути частиною індексу => це виконується
- Усі поля в проекції мають бути частиною індексу => не виконується, бо нема проекції
- Поле _id має бути явно виключене з проекції (якщо тільки воно не є частиною індексу) =>  не виконується, бо нема проекції
Тобто до запиту треба ще додати 2й параметр - проекцію з вімкненими параметрами track_genre, popularity і вимкненми _id. 
В результаті покривний запит може виглядати так:
```
db.tracks.find(
  {
    track_genre: "pop",
    popularity: { $gte: 70 }
  },
  { //проекція
    track_genre: 1, 
    popularity: 1,
    _id: 0  // вимкнений _id
  }
);
```
